# Silent-success sweep — 2026-08-24

**One defect class: an operation reports success while producing nothing.**

Run after four instances of the class were confirmed and fixed the same day, to answer whether
those four were most of it. They were not. Seven lenses produced 23 candidates; each was then
attacked by an independent agent instructed to REFUTE it. **13 survived, 7 were refuted.**
Every finding below carries the verifier's corrections, not the reporter's original framing.

## Confirmed

### 1. [medium] GET /tasks/ silently drops due_before/due_after/updated_before/updated_after on any non-YYYY-MM-DD value, degrading to the unfiltered query with HTTP 200

GET /tasks/ silently ignores any of its four date filters (due_before, due_after, updated_before, updated_after) when the value is not bare YYYY-MM-DD, and degrades to the maximally permissive query with HTTP 200 and no warning. `_parse_date` (api/routers/task_router.py:274-281) returns None for both "no value" and "unparseable value", and the four call sites (L489-503) append a WHERE predicate only when the parse succeeds. Nothing upstream validates: the params are declared `Optional[str] = Query(None)`, the app's only middleware is CORS, and the MCP `task_list` tool (personal-koi-mcp/src/koi-api-tools.ts:1440, handler L2604) passes the string straight through behind a `type: 'string'` schema whose YYYY-MM-DD requirement exists only in the prose description. Notably, the ISO-8601 *datetime* form that `datetime.isoformat()` emits is among the silently-ignored values.

Verified impact when it fires: `?due_before=2026-08-24` returns 415 rows; `?due_before=2026-08-24T00:00:00Z` returns 4262 — the entire default-visible registry — of which 3825 have due_date IS NULL and cannot be overdue at all. The caller cannot distinguish this from a legitimately unfiltered query.

Two corrections to the original report. (1) The blast-radius figure is wrong: "~500 tasks" was the reporter's own `limit=500` cap; the registry holds 5880 rows, 4262 visible by default, only 835 with any due_date. (2) Reachability of the failure is not demonstrated. The endpoint is live and actively queried with date filters — 15,356 `GET /tasks` requests over ~6.5 months of stdout.log — but all 82 distinct date values ever logged were tested against `date.fromisoformat` and every one of the 75 organic values parsed correctly; the only 7 failures in the entire log are probes generated by this investigation. This is therefore a real, reproducible, undocumented latent defect on a live path with zero recorded organic occurrences — not an actively-firing incident. It is in-class as "a rejected input silently substitutes the permissive default", though it is the inverse of the exemplars: it returns too much rather than producing nothing.
