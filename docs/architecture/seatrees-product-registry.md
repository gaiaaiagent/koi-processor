# SeaTrees Bloom export: product registry and coverage probe

**Status:** design approved 2026-08-12, not yet implemented beyond containment
**Incidents:** INC-20260812-001 (this work), INC-20260812-002 (related, out of scope)
**Scope owner:** Symbiocene Labs / gaia

## Problem

The SeaTrees Bloom retirement export is generated by `scripts/seatrees_bloom_export.py`
and served at `https://regen.gaiaai.xyz/seatrees/bloom-export`. It was written for a
single product, the SeaTrees+ mangrove credit (`MBS01-001`).

Seven of its 23 columns were global Python constants, and project name came from a
lookup table with one entry. When a second project appeared in the same credit class,
every one of those values silently defaulted to the mangrove product's:

- `credit_price` emitted `3` regardless of product.
- `purchase_amount`, a money column feeding a partner's accounting, is derived from
  that constant and was understated by the same factor.
- `project_name` was blank, and `project_developer` fell back to a bech32 admin address.
- `credit_scheme`, `transaction_description`, `activity_type`, `credit_size`,
  `credit_length` and `avg_price_per_hectare_per_year` all carried mangrove values.
- `project_country` and `project_region` degraded to a bare ISO code and a blank,
  because the two new jurisdictions were absent from `COUNTRY_CODES`.

Nothing errored. The CSV looked complete.

### Verified impact

Ledger state confirmed 2026-08-12 via `rest.cosmos.directory/regen`:

| Project | Jurisdiction | First batch issued | Retirements | Status |
|---|---|---|---|---|
| MBS01-001 | KE | 2024-10-19 | 23 | registered, correct |
| MBS01-002 | CR-P (Costa Rica) | 2026-05-13 | 4 | unregistered, **wrong rows delivered** |
| MBS01-003 | ES-PM (Balearic Is.) | 2026-06-01 | 0 | unregistered, latent |

Four delivered rows, dated 2026-06-22 (x2), 2026-07-03 and 2026-08-10, totalling six
credits. `purchase_amount` emitted $18.00 in total; at the reported price of 40 the
correct figure is $240.00, an understatement of $222.00. The reported price of 40 is
from the partner and is not independently confirmed.

The exporter was last modified 2026-05-04, nine days before `MBS01-002` was issued.

### Root cause

Commercial product facts lived as literals inside application code. Adding a product
required a code change plus an operator-gated promotion to a host we do not control,
so the cheap path was to let the default ride. There was no mechanism that could
notice the divergence, and the detector of last resort was the partner.

## Decisions

Four decisions were taken during design, each with alternatives considered:

1. **On an unresolvable product, refuse the whole export.** No partial CSV. A partial
   file is indistinguishable from a complete one once it reaches a spreadsheet, and on
   a money column no output beats wrong output.
2. **Scope is the exporter only.** The `seatrees-demo` divergence (INC-20260812-002)
   and any general cross-surface pattern are explicitly deferred.
3. **The registry is an in-repo YAML file, promoted as code.** Versioned, reviewable,
   testable. This preserves the operator promotion gate, which means a new product
   still waits on a promotion, which is precisely why the probe is load-bearing rather
   than optional.
4. **The probe runs on our side first.** It needs only public ledger access, so it has
   no dependency on the production host, the database, or any secret. Proposing a
   team-visible home (repo CI or host cron) is deferred to the team review.

## Design

### Components

```
config/seatrees_products.yaml               registry (new)
  | loaded and validated at import
scripts/seatrees_bloom_export.py            refuses on gap (built)
  | imported unchanged by
api/routers/seatrees_router.py              HTTP 409 (built)

scripts/check_seatrees_export_coverage.py   probe (built, needs severities)
  | run on a schedule by
claude-heartbeat on legion2                 alerting (new, our side)
```

### Registry format

```yaml
version: 1
products:
  MBS01-001:
    name: "Mangrove Forest: Marereni"
    developer: ""                  # blank falls back to the on-chain admin address
    credit_price: 3
    transaction_description: "Purchase of Seatrees+ Biodiversity Blocks"
    credit_scheme: "Seatrees+ Biodiversity Blocks"
    activity_type: "Uplift, Stewardship"
    avg_price_per_hectare_per_year: 3000
    credit_size: 0.0001
    credit_length: 10
    source: "SeaTrees, original 2024 product definition"
    supplied_on: 2024-10-19
```

Keyed by on-chain project id. Every field must be present. `developer` is the one
field permitted to be an empty string, which explicitly means "fall back to the
on-chain admin address" and preserves long-standing `MBS01-001` behaviour. Every other
field must be present and non-empty; in particular an empty `name` is a validation
failure, because a blank project name was one of the two originally reported symptoms.

`source` and `supplied_on` record where a commercial value came from, which the
incident showed we could not answer for the number 3. They are reported by the probe,
so they have a live consumer. A field nothing reads is the same dark-surface trap that
produced this incident, which is why there is deliberately no `currency` field: no
Bloom column consumes one.

### Validation

The loader validates the entire file at import: every product carries every field, of
the right type, and non-empty except for `developer` as described above. A malformed
registry fails at startup and in the test suite rather than mid-export on a partner
request.

The three refusal conditions, already implemented, are unchanged:

1. project absent from the registry
2. registry entry present but missing a required field
3. jurisdiction whose ISO country code is unmapped

Each raises a subclass of `ExportRefusedError` carrying the project id, the batch
denom, the specific missing fields, and a paste-ready remedy. The HTTP layer maps any
of them to 409 with that detail as structured JSON. The CLI prints them to stderr and
exits 2, writing no file.

### Probe severities

| Condition | Meaning | Exit |
|---|---|---|
| every retired project registered | clean | 0 |
| retired from an unregistered project | export broken now, rows may be delivered | 1 |
| ledger unreachable | coverage unknown, never reported as clean | 2 |
| issued but unregistered, no retirements | will break on first retirement | 3 |

Exit 1 and exit 3 are separated so future breakage does not page anyone, while live
breakage does. Against current state the probe emits ALERT for `MBS01-002` and WARN
for `MBS01-003`.

Exit 2 exists because `query_retirements_with_fallback` returns an empty list both for
a genuine zero and for total provider failure. A reachability preflight distinguishes
them. Reporting "clean" for a window nobody actually checked would reproduce the
original defect inside the detector.

The probe drives every retirement through the real `build_bloom_row`, rather than
reimplementing the checks, so it cannot drift from what the export actually does.

### Testing

- **Registry loader:** valid file, missing required field, wrong type, unknown key,
  empty file, absent file.
- **Golden row regression:** `MBS01-001` output byte-identical, now sourced from YAML.
  This has been verified against the pre-change implementation by running both and
  comparing, not by asserting a transcribed expectation.
- **Refusal contract:** the 15 tests already written, covering all three conditions,
  each commercial field individually, and a correctly registered second product.
- **Probe:** fixture-driven with no network, covering each severity and the
  unreachable-ledger path.
- Every guard mutation-tested: break the implementation, confirm a test notices.

## Out of scope

- `seatrees-demo` and its divergent seed data (INC-20260812-002).
- Any admin endpoint or authenticated write surface.
- Any SeaTrees-supplied price feed.
- Resolving `regen:` metadata IRIs, which requires a data server that is not publicly
  reachable. Until that changes, `name` and `developer` remain hand-maintained. Fixing
  it later removes two keys from the registry, not the registry itself.
- Removing or altering the operator promotion gate.

## Open questions

- The correct commercial values for `MBS01-002`. Only SeaTrees can supply them; the
  price of 40 is reported, not confirmed.
- Whether `MBS01-003` is a live SeaTrees product at all. It has never been retired
  from, so no wrong data has been delivered from it.
- Whether SeaTrees has already entered any of the four affected rows into accounting,
  which determines whether correction is a reissue or a restatement.

## Already implemented

Containment landed on branch `fix/bloom-refuse-unregistered-projects` before this
design was written, under explicit approval, because it stops ongoing wrong output and
its shape does not change under any option considered here:

- per-project registry as a Python dict, to be replaced by the YAML in item 1
- all three refusal conditions with paste-ready remedies
- HTTP 409 on the endpoint, exit 2 on the CLI
- `CR` and `ES` added to `COUNTRY_CODES`
- the coverage probe, at single severity
- 15 tests, with mangrove output proven byte-identical to the previous implementation
